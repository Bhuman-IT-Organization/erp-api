# identity

## Purpose

Administration of **who may sign in and what they may do**: the staff members, the roles and ownership of the permission rows. Wave 0 moved sign-in itself to `v1/auth`; this module moves the screens that hand out access.

ADR-0034 makes this the **only** module that writes `tblstaff`, `tblstaff_permissions` and `tblroles` — a business module has nowhere to write, so the legacy escalation path (eight permission screens, four of them reachable by a non-admin) cannot be reintroduced. Two rules follow from that and are the reason this module exists rather than a `staff` CRUD:

- **Granting is admin-only and is never gated by a permission code** (decision 2). A code can be handed out by the mechanism it protects.
- **Every granting change writes exactly one append-only audit row in the same transaction as the change** (decision 3). Perfex's activity log cannot say who escalated whom; `tblidentity_audit` can, from the first commit.

Both halves are built: plan 03.1-12 the members and the audit read, plan 03.1-11 the roles, the permission catalogue, the departments picker, the three role events and the facade method `v1/auth` reads permissions through.

## Facade surface

- `describe(): { module: 'identity'; version: 1 }`
- `permissionsOf(staffId): Promise<readonly PerfexPermissionRow[]>` — the stored `tblstaff_permissions` rows in Perfex's own `feature`/`capability` format. The **only** cross-module surface, and the one synchronous call brief §7 justifies: login must answer with the member's current permissions in the same request. `v1/auth`'s enricher translates them into clean ADR-0033 names, exactly as it did when it read the table itself.
- `contactOf(staffId): Promise<StaffContact | null>`: one member's `{ email, locale, active }` for another module's email, the locale through `toLocale` (null when empty or unknown), null for an unknown id. `v1/mail` reads it, so it never names `tblstaff` (04.3 PATTERNS M1).
- `listActiveMembers(): Promise<readonly StaffName[]>` and `namesOf(staffIds): Promise<ReadonlyMap<number, string>>`: members named "first last" and nothing else (M13); the staff directory identity registers with `v1/departments` wraps them (D-49).

Other modules import only `src/v1/identity/index.ts`. Its consumers: `v1/auth` and `v1/mail`.

**`profileImageUrl` is a path this module builds, never a stored file name.** `tblstaff.profile_image` holds the bare name Perfex's uploader wrote; the transformer answers `/uploads/staff_profile_images/<staffId>/small_<file>` — the same-origin path `helpers/staff_helper.php:236` serves — or `null` when the column is empty or the name is refused. `small_` is the 96 px copy the legacy staff LIST renders (`tables/staff.php` takes the helper's default `$type`); Perfex's uploader also writes a 320 px `thumb_` copy, which ships as `profileImagePreviewUrl` on the list row and the detail because the list's image preview needs it (D-23); both URLs are built behind the same `isSafeFileName` guard, so a name it refuses is `null` for both. Perfex keeps the uploaded name, spaces and parentheses included (`unique_filename`), so `isSafeFileName` refuses only an empty or over-255-character name, a `/` or `\`, `..`, a leading dot or a control character, and the name segment is percent-encoded (`encodeURIComponent`), so `42010_Jane Doe_0.jpg` is served as `small_42010_Jane%20Doe_0.jpg`. The upload itself stays on Perfex (§9.1): Node reads the column and never writes it.

**`roleName` is on the list row, not a join the client makes.** `views/admin/tables/staff.php` renders `roles.name` to anyone who may view staff, but `GET roles` is administrator-only (ADR-0034 d.3, the 2026-09-24 decision) — so a Role column resolved by reading the roles list is blank for every non-administrator. The list row therefore carries the name itself, resolved exactly as the member detail resolves it (`tblroles.name` for `tblstaff.role`): `null` when the member holds no role, and `null` — never an error — when the id no longer resolves, because `tblstaff.role` carries no foreign key (SF-7). The whole page's names come from ONE `findRoleNamesByIds` read, the shape `memberCount` uses on the roles list, so the list is two queries whatever the page size and never one per row.

**`lastLogin` and `lastActivity` are read-only ISO strings, each on the shape whose legacy view renders it.** `tables/staff.php`'s fourth column is `last_login`, so the list row carries `lastLogin`; `views/admin/staff/member.php` shows Last Active beside the member's name, so the member response carries `lastActivity` as well as `lastLogin` (the detail shape is a documented superset of the list row). `null` is what Perfex renders as "Never"; the api formats no date. `v1/auth` still writes `last_login` and Perfex still writes `last_activity` — this module only reads them.

**`GET locales` is the counterpart of Perfex's `get_available_languages()`, and it is deliberately not the same list.** Perfex builds its select by listing `application/language/` (28 pack folders on the client's copy); this api may not read the legacy filesystem, and offering a language erp-web has no message pack for would be a promise the build does not keep. So the source of truth is `SUPPORTED_LOCALES` in `shared/config/legacy-locale.ts` — the set erp-web's `src/i18n/locales.ts` ships, `en` and `ar` today — and a unit test compares the two lists whenever the sibling repository is checked out. Each row carries the BCP-47 `locale` and the `legacyLanguage` name to submit as `defaultLanguage`, so a value written here is one Perfex's own screens still understand. "System Default" is the web's `null`, not a row. `LEGACY_LANGUAGE_TO_LOCALE` stays the longer, _reading_ direction: a stored value has to be understood even when the new stack has no messages for it.

A write body is **strict**: an unknown key is a 400, so a mistyped granting field is never silently ignored. All three lists are keyset-paged. The audit log pages on the row id (newest first), so its `sort` accepts only `createdAt` and its cursor is a decimal id; the members and roles lists speak the list grammar below. The catalogue, the departments picker and the locale list are not paged: none of them is a keyset read, so each carries `meta.total` and no cursor (the catalogue and the locales are not table reads at all).

**List grammar (members and roles, plan 03.2-01).** `?sort=` takes one field — members `staffId` (the default), `firstName`, `email` or `active`; roles `roleId` (the default) or `name` — with a leading `-` for descending; any other field, or a compound sort such as `sort=firstName,email`, is a 400 `ERP-VALIDATION-0001`. Role and Last login are **not sortable** (D-41): the role name is a join and `last_login` is nullable, so neither is a keyset key (a role's `memberCount` is an aggregate and does not sort either). Paging is keyset on `(sortField, id)` with an **opaque cursor** — base64url JSON of the sort field, the row's `[value, id]` and a direction (`shared/http/keyset.ts`) — so a cursor from one sort sent with another, or a tampered one, is the same 400. The meta is `{ nextCursor, prevCursor, total, rangeStart }`: `total` counts every row the filters and `q` match (never the cursor), `rangeStart` is the 1-based rank of the page's first row (`0` on an empty page), and `prevCursor` / `nextCursor` are `null` on the first / last page — the pager's "Showing 1–25 of 1,240", Previous and Next. `GET roles` takes the same `q` as the members list (the role name, at most 100 characters). A member row and the member detail carry two image URLs: `profileImageUrl` (`small_`, 96 px, the list thumbnail) and `profileImagePreviewUrl` (`thumb_`, 320 px, the preview); neither is ever the original upload, which Perfex deletes.

**Export (plan 03.2-05, D-26 and D-42; plan 04.1.1-02, ADR-0043).** `GET members/export` and `GET roles/export` export **every** row the list's current query matches, not one page, as CSV, Excel, PDF or print rows. They take the list's query (`q`, `filter[...]`, one `sort`) minus `limit` and `cursor`; sending either is a 400, never ignored. Each is gated exactly like its list, for every format: members on `staff.members.view`, roles on the administrator flag asserted in the service before any parse or count (no code), and `route-gates.spec.ts` classifies both handlers (one handler per list). **The shared core does the rest** (`shared/http/export.ts`): the service hands `parseExportOptions` the raw query and `runExport` its cells, its count and its keyset read; the module keeps no loop, cap check or file type of its own. **Parameters**, each refused with 400 `ERP-VALIDATION-0001` on its own path: `format` is `csv` (absent), `xlsx`, `pdf` or `print`; `column` names a subset of the columns, answered in canonical order (D-13); `header` carries the web's translated labels, one per exported column, each at most 100 characters (D-42; absent writes the wire field names); `key` is always refused here, because neither list has a row selection (D-27); and for `pdf` and `print` only, `title` (at most 100 characters), `yes`, `no`, one `blank` per column, `dateFormat` (a Perfex date format), `timeFormat` (`24` or `12`) and `timeZone` (an IANA zone, never replaced by a fallback) (D-25). **Values:** CSV and Excel carry the wire values: `active` is `1`/`0` (the api cannot translate "Active"), a missing role or login is an empty cell, `lastLogin` is ISO 8601; every text cell and header label that starts with `=`, `+`, `-`, `@`, TAB or CR is prefixed with `'` (OWASP CSV injection); CSV has a UTF-8 BOM (so Excel reads Arabic names), RFC 4180 quoting and CRLF line ends, and Excel never writes a formula. PDF and Print carry the display values: `active` reads the sent `yes`/`no`, an empty cell its column's `blank`, and `lastLogin` the sent date format, time format and zone. A PDF whose text the standard font cannot draw (an Arabic name) is refused with 400 on the `font` path (D-24); Print of the same list answers it, because the browser draws it. **Caps:** the core counts the matching rows first (`countMembers` / `countRoles`, the list's own `where`) and refuses more than 10,000 for csv and xlsx, or 1,000 for pdf and print, with 400 on the `export` path and `params: { limit, total }`, before any row is read; otherwise it reads with the list's keyset query in batches of 500, following `nextCursor`. Both list metas carry `exportLimit` 10,000 and `printLimit` 1,000. **Headers:** each file answers its `Content-Type`, `Content-Disposition: attachment; filename="<stem>-YYYY-MM-DD.<csv|xlsx|pdf>"` (a constant stem and the UTC date, no request input) and `Cache-Control: no-store`; print answers `application/json; charset=utf-8` rows `{ exportedAt, headers, rows }` with `no-store` and no attachment. The static `export` segment wins over `:id` in Fastify's router, so `members/export` is never read as a member id (the e2e spec pins it).

**No roles endpoint declares a permission code at all, reads included since 2026-09-24.** The three writes never did: `staff.roles.create`, `staff.roles.edit` and `staff.roles.delete` stay in the `@erp/contracts` mapping (it must be 1:1 with every active Perfex code, and Perfex's own roles screen still checks them during coexistence) but a bearer holding all three is refused **403 `ERP-IDENTITY-0001`** by `POST`, `PATCH` and `DELETE /roles/:id`. The migration lead then closed the reads the same way: `GET /roles` and `GET /roles/:id` used to run on `staff.roles.view` (the second also admitting `staff.members.view`), while erp-web's menu already hid `/setup/roles` behind `is_admin()`, so a non-administrator holding that one code could read every role's full permission template, a capability Perfex never granted and no screen exercised. Both now assert the administrator flag in the service and answer **403 `ERP-IDENTITY-0004`**, exactly as `GET audit` does; `staff.roles.view` stays in the catalogue as a declared code rather than being deleted. The member form is unaffected: its role select is an administrator's control (ADR-0034 d.2), and erp-web's `use-identity-lookups.ts` already treats a refusal of the roles list as "no role names", never as a screen error.

**Where that gate is declared: `ROUTE_GATES` in `@erp/contracts`, once.** The drift above existed because the gate was written down twice — here and in erp-web's `config/navigation.ts` — with nothing comparing them. `packages/contracts/src/route-gates.ts` maps each erp-web route to a clean permission code or the literal `'admin'`; erp-web derives its menu flags and route helpers from a mirror of it, and `src/v1/identity/__tests__/route-gates.spec.ts` asserts every handler above matches it (a route gated `'admin'` carries no `@Permissions` and its service method asserts the flag; a route gated on a code carries exactly that code). **The map is not a runtime gate on either side**: this module keeps authorising per handler, and in erp-web the map is a UI declaration and a test oracle only.

## Events subscribed

None, and that is a decision rather than a gap: identity is the authority on who may do what, so nothing another module publishes changes a row it owns (ADR-0034 decision 1). The traffic runs the other way — `v1/auth` subscribes to `identity.member.passwordChanged` and `identity.member.deactivated` (end the member's sessions: delete every `auth:sess:*` and bump the token version), to `identity.member.accessChanged` (end the sessions and drop `auth:perm:{staffId}`, because the admin flag and the role are baked into both) and to `identity.permissions.replaced` (drop `auth:perm:{staffId}`).

## Jobs

None. A `jobs/` folder arrives with `shared/queue/` (built by the first module that needs a job; the module-shape spec rejects `jobs/` until then).

## Resilience

The module makes no outbound call in Wave 1; the three bullets are the identity-access brief §6.1 verbatim.

- **Breaker:** none — the module makes no outbound call in Wave 1 (the welcome e-mail is dropped, §10 Q7)
- **Retry policy:** none on writes; member and role saves are never retried
- **Pool budget:** shares `POOL.db.api`; no Redis client of its own (snapshot invalidation goes through the `auth` event subscription, §7)

## Security notes

- **Granting is administrator-only** (ADR-0034 decision 2). A request that would set or change a member's `role`, permission set or `administrator` flag needs `tblstaff.admin = 1` on the **actor**, read from the verified bearer — never a permission code, whatever codes the actor holds. `service/granting-policy.ts` is the one place that answers "is this change a grant, and may this actor make it?", and every write path calls it.
- **Every identity change is audited** (ADR-0034 decision 3). One append-only `tblidentity_audit` row per change — actor, subject, what changed, before, after, the `x-request-id` and the timestamp — written inside the same transaction as the change, so a change without a row cannot commit. `IdentityAuditRepository` exposes `append` and `list` and nothing else; a grep gate asserts the module contains no `identityAudit` update, delete or upsert.
- **The audit and the gate read what is persisted, never the request body** (quick 260925-rvw, review WR-03/04/12). A member save compares the member's stored `tblstaff_permissions` rows with the rows it will leave: none for an administrator (so a promotion clears the rows and audits each removal, and a demotion brings nothing back), the stored rows untouched when the body has no `permissions`, and otherwise the requested codes (no `leads` for an is_not_staff member) **plus every stored row the ADR-0033 mapping does not know, carried through**. The rows are rewritten only when that comparison differs, and `identity.permissions.replaced` is published only then. A removed unmapped row is audited by its raw `feature:capability` (a colon, so it never reads as a clean name). The `applyToMembers` fan-out uses the same comparison.
- **The other administrator-only rules of brief §5 are enforced on the server, not by hiding a control**: staff id 1 keeps admin, nobody removes their own admin, a non-admin cannot change an admin's password or status, nobody deactivates themselves. Perfex enforced several of these only by hiding UI — a recorded legacy privilege-escalation finding, not a behaviour to copy.
- **A role IS a permission set, so every role write is a grant** (ADR-0034 decision 2 and brief §5's 2026-09-23 correction table). `POST /roles`, `PATCH /roles/:id` and `DELETE /roles/:id` run on `tblstaff.admin = 1` and declare **no** permission code: creating, renaming, re-templating or deleting a role changes what every holder may do, and there is no profile half to let a non-administrator through the way `staff.members.edit` has one. Delete is included because it is a write to `tblroles`, and one role write left on a grantable code would reopen the hole.
- **A role write cannot clear the last administrator, structurally.** `tblroles` carries no administrator column — the flag lives on `tblstaff` and only a member save moves it — and an administrator holds no permission rows at all by Perfex's own rule, so the `applyToMembers` fan-out skips administrators and has nothing to take from them. The reachable form of the rule is on the member side: a save that would leave no `tblstaff.admin = 1` row is refused `ERP-IDENTITY-0004`, beside brief §5's staff-id-1 and own-flag rules.
- **A clean permission name the ADR-0033 mapping does not know fails the save** (`ERP-IDENTITY-0003`) rather than writing an invented Perfex row — on a member's rows and on a role's template alike.
- **The departments picker reads `DepartmentsFacade` (D-55)** and answers `departmentId` and `name` only, built key by key and `parse`d (threat T-3.1-51); identity names no departments table. A member save refuses a department id that is new for the member and unknown to the facade (422 `ERP-IDENTITY-0009`), before any write; a stored link to a deleted department is kept and still saves.
- No DTO carries a password hash, a token or a column brief §2.1 leaves to Perfex; the transformer `parse`s every response so nothing rides along.

## Dropped on purpose

From brief §9.1 — deliberate, agreed with the lead, and not to be built back in:

- the welcome e-mail (it sent the new member's password in plain text; Node has no e-mail port yet);
- staff delete (about 40 tables other modules own — Perfex keeps it; Node offers deactivate);
- the profile-image **upload** (the files and their resized copies live on Perfex's disk) — its **display** is not dropped: `profileImageUrl` names the 96 px copy so a migrated screen renders the same photo, and `profileImagePreviewUrl` the 320 px copy for the preview;
- sorting the staff list by **Role** or **Last login** (D-41) — the legacy DataTable sorts both, but neither is a keyset key (a join; a nullable column), so neither column offers a sort;
- staff custom fields (none are defined) and staff notes;
- marking every current announcement dismissed for a new member (`tbldismissed_announcements` is not ours);
- the hidden `fakeusernameremembered` / `fakepasswordremembered` inputs (a browser workaround with no behaviour);
- the role permission codes as gates: `staff.roles.create`, `staff.roles.edit`, `staff.roles.delete` **and, since the migration lead's 2026-09-24 decision, `staff.roles.view`** stay in the `@erp/contracts` mapping for Perfex's own screens but gate nothing on the roles endpoints here: a deliberate divergence from the 1:1 rule, recorded in brief §9.1 (ADR-0034 decision 2, `ROUTE_GATES['/setup/roles'] === 'admin'`). `staff.roles.view` still admits `GET permissions/catalogue`, which is the list of 507 code NAMES rather than any role's template (brief §5);
- any write to `tblactivity_log` — the §7 events, the structured logs and `tblidentity_audit` are the record.
