# auth

## Purpose

Identity for the whole ERP from wave 0 (ADR-0005, ADR-0030): verifies a staff member's legacy `tblstaff` bcrypt hash, re-hashes it at cost 12, issues an RS256 access token and a rotating refresh token kept (hashed) in Redis, and publishes the JWKS the legacy `erp_sso` module verifies against. It is the reference implementation of every backend layer (erp-docs `01-onboarding/02-first-feature.md` walks it file by file).

Status: complete for wave 0 — every layer present with its spec; the facade resolves through the module (`__tests__/auth.facade.spec.ts`) and the HTTP contract is proven in-process (`__tests__/auth.controller.e2e.spec.ts`) and against the local stack (`src/__tests__/app.e2e.int.spec.ts`).

## Owned tables

- `tblstaff` — **three columns, and no others**: `password` (the compare-and-set re-hash on login), `last_login` and `last_ip`. **Every other column of the row belongs to `v1/identity`**, which ADR-0034 decision 1 makes the only module that writes identity — the profile columns, `role`, `admin`, `active`, `is_not_staff` and the password an administrator _sets_ are all written there (identity-access brief §2.1). These three are the one recorded, **column-scoped** exception to that decision, and they are an exception to the table rule rather than to the decision: none of them grants anything. `last_password_change` is never touched by a re-hash (Perfex's password-expiry check keys on it), and `last_activity` and the profile edits stay Perfex's during coexistence (ADR-0030).
- **`tblstaff_permissions` is no longer read here** (plan 03.1-11). It used to be, through `$queryRaw`; ADR-0034 decision 1 gave the table to `v1/identity`, so `AuthService` now reads the rows through `identity.facade.permissionsOf(staffId)` — the one synchronous cross-module call brief §7 justifies, because a login must answer with the member's current permissions in the same request. `AuthRepository.listPermissions` is deleted, not deprecated, and the `src/v1/__tests__/module-shape.spec.ts` identity-tables clause fails the build if any file of this module names the table again. `tblroles` was never read here.

That sentence is what `STAFF_TABLE_ALLOWLIST` in `src/v1/__tests__/module-shape.spec.ts` points at: the clause lets `identity` and `auth` name `tblstaff` and refuses every other module, and `auth`'s entry is legitimate only while this list stays three columns long.

## Facade surface

- `verifyAccessToken(token): Promise<AuthenticatedUser | null>` — implements `ACCESS_TOKEN_VERIFIER` (`shared/http/auth/`): RS256 by `kid`, then token version and revoked `jti` from Redis. `null` on any failure.
- `hasPermission(staffId, code): Promise<boolean>` — from the `auth:perm:{staffId}` snapshot; `code` is a clean ADR-0033 name from `@erp/contracts`, never a Perfex code; admin implies true.
- `describe(): { module: 'auth'; version: 1 }`
- `AUTH_HTTP_SECURITY` — the only non-facade export: HTTP security constants for the composition root (`main.ts` hands them to `shared/http/fastify-plugins.ts`, because `shared/` may not import `v1/`): the CSRF cookie name and path, the `x-csrf-token` header, the three POST paths the CSRF hook protects, and `sessionEnd` (the refresh path, the codes 0002/0003 and `SESSION_COOKIES`) for the hook that clears both session cookies when a refresh ends the session (ADR-0037).

Other modules import only `src/v1/auth/index.ts` (the facade, its public types, `AUTH_HTTP_SECURITY`). `AuthModule` is `@Global()` and provides `ACCESS_TOKEN_VERIFIER` (`useExisting: AuthFacade`), so `JwtAuthGuard`/`PermissionGuard` work in every module without an import.

## Endpoints

Under `api/v1/auth` (`AUTH_ROUTES` in `auth.routes.ts`). Every failure is an RFC 9457 problem (`application/problem+json`) with an `ERP-*` code; wrong e-mail, wrong password and inactive account all answer the same generic 401.

| Method | Path                                                          | Guard                               | CSRF               | Cookies                                                                                                                                      | Success                                                                                                                                                                      | Errors                                                                                                                  |
| ------ | ------------------------------------------------------------- | ----------------------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `POST` | `login`                                                       | none (Nginx `limit_req`)            | no (no cookie yet) | sets `erp_refresh` (path `/api/v1/auth/refresh`, 30 d), `erp_csrf` (path `/api/v1/auth`, session) and `erp_session_present` (path `/`, 30 d) | 200 `loginResponseSchema` (`csrfToken` in the body)                                                                                                                          | 400 `ERP-VALIDATION-0001`, 401 `ERP-AUTH-0001`, 403 `ERP-AUTH-0007` (two-factor), 429 `ERP-AUTH-0006` + `Retry-After`   |
| `POST` | `refresh`                                                     | none (the cookie is the credential) | `x-csrf-token`     | rotates `erp_refresh` and re-sets `erp_session_present`; keeps `erp_csrf`                                                                    | 200 `loginResponseSchema` (new access token, new `csrfToken`)                                                                                                                | 401 `ERP-AUTH-0002` (missing/unknown), 401 `ERP-AUTH-0003` (reuse: family revoked, version bumped), 403 `ERP-AUTH-0008` |
| `POST` | `logout`                                                      | bearer                              | `x-csrf-token`     | clears `erp_refresh` and `erp_session_present`                                                                                               | 204                                                                                                                                                                          | 401 `ERP-AUTH-0004`, 403 `ERP-AUTH-0008`                                                                                |
| `POST` | `logout-all`                                                  | bearer                              | `x-csrf-token`     | clears `erp_refresh` and `erp_session_present`                                                                                               | 204 (every session deleted, version bumped)                                                                                                                                  | 401 `ERP-AUTH-0004`, 403 `ERP-AUTH-0008`                                                                                |

| `GET`  | `csrf`                                                        | none                                | no                 | sets `erp_csrf` when absent                                                                                                                  | 200 `csrfResponseSchema` (a fresh token for a page that lost its in-memory one)                                                                                              | —                                                                                                                       |
| `GET`  | `legacy-sso`                                                  | bearer                              | no                 | —                                                                                                                                            | 200 `{ status: 'ready' \| 'inactive' }` — readiness of the legacy `erp_sso` module through the `legacy` breaker; `status` only, the transport's `detail` is logged, not sent | 401 `ERP-AUTH-0004`, 503 `ERP-UPSTREAM-0001` + `Retry-After` (breaker open, or legacy down after the retries)           |
| `GET`  | `/.well-known/jwks.json` (unprefixed, `WELL_KNOWN_JWKS_PATH`) | none                                | no                 | —                                                                                                                                            | 200 `jwksResponseSchema`, public members only, `Cache-Control: public, max-age=TIMINGS.auth.jwksCacheMaxAgeS`                                                                | —                                                                                                                       |

`GET me`'s `permissions` are **clean ADR-0033 names** (`staff.members.view`, `sales.invoices.view`, …), never Perfex codes: `service/auth.enricher.ts` translates the `tblstaff_permissions` rows through the `@erp/contracts` mapping when it builds the snapshot, and it is the only code in the api that reads a Perfex code (ADR-0033 decision 2). `POST refresh` **rebuilds** that snapshot rather than reusing the cached one (ADR-0033 decision 6), so a permission revoked in Perfex stops working in Node within one access-token lifetime (`TIMINGS.auth.accessTokenTtlMs`, 15 minutes) instead of surviving for the refresh TTL; the cost is one small indexed query per staff member per refresh.

`user.locale` (login, refresh) and `me.locale`: BCP-47 from `tblstaff.default_language` via `shared/config/legacy-locale.ts` (`LEGACY_LANGUAGE_TO_LOCALE`, `toLocale`); `null` when unset or unknown. Additive (plan 03-01); erp-web writes its `erp_locale` cookie from it after a successful login.

Cookie attributes: `erp_refresh` is `HttpOnly; SameSite=Strict; Path=/api/v1/auth/refresh; Max-Age=TIMINGS.auth.refreshTokenTtlMs/1000`, `Secure` iff `AUTH_COOKIE_SECURE`; `erp_csrf` is `HttpOnly; SameSite=Strict; Path=/api/v1/auth`, `Secure` iff `AUTH_COOKIE_SECURE`, no `Max-Age` (a session cookie holding the double-submit secret). The CSRF check is an `onRequest` hook (`shared/http/fastify-plugins.ts`) on exactly the three POST paths in `AUTH_HTTP_SECURITY.csrfProtectedPaths`; `login` is never checked because no cookie exists before it. `erp_session_present` is `HttpOnly; SameSite=Lax; Path=/; Max-Age=TIMINGS.auth.refreshTokenTtlMs/1000`, `Secure` iff `AUTH_COOKIE_SECURE`, value `1` (ADR-0032): it authorises nothing and is read only by erp-web's `proxy.ts`, which uses it to choose between rendering the shell and redirecting to `/login` — a forged or stale one buys a rendered shell and a 401 from the first API call. One controller helper per direction sets or clears it together with `erp_refresh`, and a refresh answered 0002/0003 clears both through the `onSend` hook in `shared/http/fastify-plugins.ts`, from the same `SESSION_COOKIES` (ADR-0037), so the two cannot drift; a refresh refused 0008 (CSRF) or answered 5xx clears neither; `erp_refresh`'s narrow path is never widened (ADR-0032 rejects that explicitly). Refresh tokens are `${staffId}.${sid}.${secret}`; only `sha256(secret)` is stored.

## Events published

Declared in `events/published.ts`, published through `DOMAIN_EVENT_PUBLISHER` (`shared/events/`). Payloads are ids and labels only.

| Name                     | Class                     | Payload                                                                                                    |
| ------------------------ | ------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `auth.login.succeeded`   | `StaffLoginSucceededV1`   | `{ staffId, sessionId, at }`                                                                               |
| `auth.login.failed`      | `StaffLoginFailedV1`      | `{ staffId: number \| null, reason: 'invalid_credentials' \| 'inactive' \| 'two_factor' \| 'locked', at }` |
| `auth.password.rehashed` | `StaffPasswordRehashedV1` | `{ staffId, fromLabel, toLabel: '$2y$12$', at }` — 7-character bcrypt labels, never hashes                 |

## Events subscribed

Four, all `v1/identity`'s (identity-access brief §7, plus `identity.member.accessChanged` from review CR-02 a of Phase 3.1). Listed in `events/subscribed.ts`; the handler is `events/handlers/identity-access.handler.ts`, which registers on the shared `DOMAIN_EVENT_SUBSCRIBER` port from its own `onModuleInit` — nothing here imports `v1/identity`'s `events/` (BE-03), the names are the contract.

| Event                             | Effect                                                                                                                                                                                                          |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `identity.member.passwordChanged` | `AuthService.endSessionsOf` — delete every `auth:sess:*` of the member and bump the version, so a refresh cookie and an access token issued before it both fail                                                 |
| `identity.member.deactivated`     | `AuthService.endSessionsOf` — delete every `auth:sess:*` of the member and bump the version, so a refresh cookie and an access token issued before it both fail                                                 |
| `identity.member.accessChanged`   | `AuthService.endSessionsOf`, then `AuthService.dropPermissionSnapshot` — the admin flag and the role are baked into the access token and the snapshot, so the sessions end and `auth:perm:{staffId}` is deleted |
| `identity.permissions.replaced`   | `AuthService.dropPermissionSnapshot` — delete `auth:perm:{staffId}` so the next request rebuilds it (ADR-0033 decision 6)                                                                                       |

The token version is **not** bumped on a permission change: the member is still who they were, only what they may do changed. Delivery is in-process and happens after the writing transaction commits, and a handler that throws is contained by the publisher — a notification's subscriber must never turn a committed change into a 500. The refresh rebuild (ADR-0033 decision 6) stays the backstop if the event never arrives, so a permission revoked in Perfex still stops working within one access-token lifetime.

## Resilience

ADR-0031: every outbound call goes through `src/shared/resilience/` from `service/auth.transport.ts` and nowhere else. `service/auth.service.ts` contains no `withRetry`, no `BreakerRegistry` and no `fetch` (enforced by the `no-restricted-syntax` (`fetch`) and `no-restricted-imports` (`shared/resilience/*`) scopes in `eslint.config.mjs`, proven by `corepack yarn check:arch`).

- **Breaker: legacy** — `service/auth.transport.ts#probeLegacySso` (opossum via `shared/resilience/breaker.ts`; created at construction, so `/api/v1/health` lists `checks.breakers.legacy` as `closed` from boot). `405` + `X-Erp-Sso: active` → `ready`; `405` without the header → `inactive` (`present-not-activated`); `404` → `inactive` (`absent`); 5xx/network → retried, then `UpstreamHttpError`/the fetch error; the value is cached `TIMINGS.http.legacy.probeCacheMs`. Open breaker → `UpstreamUnavailableError` with zero network calls → 503 `ERP-UPSTREAM-0001` + `Retry-After: ceil(halfOpenAfterMs / 1000)` from the shared filter; `status` on `/health` stays `ok` (an open breaker is the upstream's outage, not ours).
- **Retry policy: `RETRY_POLICIES.legacyHttp`** on the probe only (an idempotent GET). **login/refresh/logout are never retried** — the lockout counter makes a retried verify non-idempotent (ADR-0031 §2): one bad password must count exactly once.
- **Pool budget:** shares `POOL.db.api` (10 per api replica, `connection_limit` in `DATABASE_URL`, asserted by `check:db`); one extra ioredis client on DB `AUTH_REDIS_DB` with the `TIMINGS.redis` fail-fast options (`lazyConnect`, `enableOfflineQueue: false`, `maxRetriesPerRequest`, connect and command timeouts — `repository/redis-auth-session.store.ts`, connected in `onModuleInit` so an unreachable auth Redis fails the boot); no other connection.

## Redis keys

Exactly these keys, on Redis DB `AUTH_REDIS_DB` (`1` locally) through the module's own client. Built by `authKeys` in `repository/auth-session.store.ts`; e-mail keys are lowercased and trimmed by the caller.

| Key                            | Content                                                                      | TTL                                        | Purpose                                                                          |
| ------------------------------ | ---------------------------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------- |
| `auth:sess:{staffId}:{sid}`    | JSON `{ refreshHash, family, device, ip, createdAt, lastSeenAt, expiresAt }` | sliding `TIMINGS.auth.refreshTokenTtlMs`   | one session per device; rotation writes a new hash and keeps `family`            |
| `auth:user:{staffId}:sessions` | SET of `sid`                                                                 | none (members removed with their sessions) | logout everywhere, device limit, admin force-logout                              |
| `auth:user:{staffId}:version`  | integer (absent ⇒ 0)                                                         | none                                       | bumped on password change or ban; access tokens with an older `ver` are rejected |
| `auth:revoked:{jti}`           | `1`                                                                          | remaining token life                       | immediate revocation of one access token (logout)                                |
| `auth:perm:{staffId}`          | `PermissionSnapshot` JSON — clean ADR-0033 names                             | `TIMINGS.auth.refreshTokenTtlMs`           | `PermissionGuard` never hits MySQL per request                                   |
| `auth:lockout:{email}`         | JSON `{ failures, lockedUntil }`                                             | `TIMINGS.auth.lockoutWindowMs`             | keyed on the e-mail so unknown accounts are throttled too                        |

`auth:perm:{staffId}` holds clean ADR-0033 names only; the TTL is the session's outer bound, not the freshness guarantee — every token refresh rebuilds the snapshot from the rows (ADR-0033 decision 6). `AuthSessionStore` carries the third sibling of `setPermissions`/`getPermissions`: `deletePermissions(staffId)` (`DEL auth:perm:{staffId}`, an absent key is not an error), so a subscriber can drop a member's snapshot the moment their permissions change instead of waiting for the next refresh — that is the target the `identity.permissions.replaced` subscriber will use. It never touches `auth:user:{staffId}:version`, which is the token-version key and is bumped, never deleted.

## Security notes

- Wrong e-mail, wrong password and inactive account answer the same generic 401 (`ERP-AUTH-0001`); the reason goes to the log and the `auth.login.failed` event only.
- Lockout is keyed on the (normalised) e-mail, with exponential backoff from `TIMINGS.auth.lockout*`.
- No hash, refresh token or private key in any DTO, event or log line (`REDACT_KEYS` covers `password`, `refresh`, `token`, `authorization`).
- Tokens are RS256 only: `jwtVerify(..., { algorithms: ['RS256'] })`; an HS256 token signed with the public key is rejected by construction. The JWKS carries `kty, n, e, alg, use, kid` and nothing else.
- Refresh tokens are stored as `sha256(secret)`; a presented token whose hash mismatches but whose `family` is known revokes the whole family.
- Password verification is `bcryptjs.compare` (constant-time inside the library); hashes are never string-compared and the cost is never parsed by hand.
