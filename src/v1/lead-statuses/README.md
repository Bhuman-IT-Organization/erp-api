# Lead Statuses

## Purpose

Migrate **Setup → Leads → Statuses** from legacy Perfex to the NestJS backend and Next.js frontend.

The feature will support administrator-only listing, searching, sorting, exporting, creating, editing, and deleting lead statuses while preserving the required Perfex behavior.

**Status:** Documentation and implementation plan. The backend module is not yet implemented.

## Owned tables

- **`tblleads_status`** — assigned to Node in `prisma/ownership.json`.
- `id` — integer primary key, generated by MySQL.
- `name` — required text, maximum 50 characters.
- `statusorder` — nullable integer controlling display order.
- `color` — nullable color value, maximum 10 characters; database default `#28B8DA`.
- `isdefault` — integer identifying built-in statuses; defaults to `0`.

Node will manage status records through the repository. The `isdefault` flag must not be accepted from create or update requests.

**Read-only dependencies:**

- `tblleads.status` — check whether any leads reference a status.
- `tblleads_email_integration.lead_status` — check whether the email integration references a status.
- `leads_default_status` — read through `SettingsFacade`, never by directly querying the settings table from this module.

No database schema change is planned.

## Facade surface

The planned `LeadStatusesFacade` will expose approved read-only methods for other NestJS modules.

Expected capabilities include:

- Retrieve one status by ID.
- List statuses for use in other modules.
- Retrieve statuses by a collection of IDs.
- Describe the module.

Other modules must use the facade rather than importing the Lead Statuses service or repository directly.

The exact method signatures will be established during implementation.

## Endpoints

The following endpoints are planned under `/api/v1/lead-statuses`.

| Method | Endpoint                       | Purpose                        |
| ------ | ------------------------------ | ------------------------------ |
| GET    | `/api/v1/lead-statuses`        | List and search statuses       |
| GET    | `/api/v1/lead-statuses/export` | Export matching statuses       |
| GET    | `/api/v1/lead-statuses/:id`    | Retrieve one status            |
| POST   | `/api/v1/lead-statuses`        | Create a status                |
| PATCH  | `/api/v1/lead-statuses/:id`    | Update a status                |
| DELETE | `/api/v1/lead-statuses/:id`    | Delete a status when permitted |

All endpoints require authentication and administrator authorization.

Requests will be validated with Zod. API responses and errors will follow the shared backend conventions.

A successful deletion will return HTTP `204`. Missing resources will return `404`. Protected or referenced statuses will receive the appropriate refusal response.

## Jobs

None. Lead Statuses management does not currently require background jobs or queue processors.

## Resilience

- **Breaker:** None required for the planned local Prisma database operations or in-process SettingsFacade access.
- **Retry policy:** No retry policy for create, update, or delete operations. Database errors must not result in an unsafe deletion.
- **Pool budget:** Use the application's existing Prisma database connection pool; this module does not create a separate connection pool.

### Business rules

1. Only administrators may list, create, update, export, or delete statuses.
2. The built-in Customer status (`isdefault = 1`) cannot be deleted.
3. A status referenced by `tblleads.status` cannot be deleted.
4. A status referenced by `tblleads_email_integration.lead_status` cannot be deleted.
5. A status configured as `leads_default_status` cannot be deleted.
6. The default-status setting must be read using `SettingsFacade`. Add `leads_default_status` to the Settings allow-list during implementation.
7. A new status receives `statusorder = existing status count + 1` when the order is omitted.
8. The name is required and limited to 50 characters.
9. Deletion refusals for referenced statuses must preserve the legacy `is_referenced` behavior.
10. Failed reference checks must never allow deletion to proceed.

## Legacy parity

The new frontend page will be available at `/setup/lead-statuses`.

The legacy list route `/admin/leads/statuses` will redirect to the new page after the frontend and infrastructure changes are complete.

The legacy deletion endpoint `/admin/leads/delete_status` must be blocked by Nginx.

**Do not block `/admin/leads/status`.** The legacy quick-add functionality must remain available for staff when `staff_members_create_inline_lead_status` permits it.

The new list will retain the legacy columns **ID**, **Status Name**, and **Options**, including the count of leads using each status.

The built-in Customer status will have an Edit action but no Delete action.

## How to run its tests

Run backend tests from `erp-api`:

`corepack yarn test`

Run integration tests:

`corepack yarn test:int`

Run the complete backend checks:

`corepack yarn check`

Required Lead Statuses tests will cover administrator authorization, validation, CRUD behavior, database operations, and every deletion refusal.

The module-shape checks will also require the module files, events declarations, and tests to exist before the complete suite can pass.
