# currencies

## Purpose

The Currencies list (W2A-05): list, read, create, update, make-base, delete and the four-format export of the client's currencies, replacing Perfex's `admin/currencies` screen (`controllers/admin/Currencies.php`, `models/Currencies_model.php`, `views/admin/currencies/manage.php`, `views/admin/tables/currencies.php`). Started as a copy of erp-docs `05-templates/backend-module` (forms: singular `currency`, plural `currencies`) and reshaped to the table's columns on the Payment Modes module's shape; the screens live under `/setup/currencies` in erp-web (a Setup > Finance item), the api under `api/v1/currencies`. The code goes through the ONE code schema in `@erp/contracts` (`packages/contracts/src/currency-code.ts`: `CURRENCY_CODE_MAX`, `toCurrencyCode`, `currencyCodeProblem`; Currencies planning answer 7), which erp-web's form holds as a byte mirror (answer 8 b). Other modules register their own uses of a currency with this module (D-41 inverted, answer 4); this module imports no other v1 module.

## Owned tables

- `tblcurrencies`: claimed for `node` in the ownership register by plan 04.1-27 (W2A-05), written here through Prisma's typed delegate, which the ownership guard admits because the register names `node`. Node writes Perfex's five form columns: `name` (the ISO code, `VARCHAR(100)`; Node writes at most `CURRENCY_CODE_MAX` = 3 characters, trimmed and upper-cased), `symbol` (`VARCHAR(10)`), `decimal_separator` and `thousand_separator` (`VARCHAR(5)`) and `placement` (`VARCHAR(10)`); a create writes all five and an update rewrites all five, as Perfex's edit does (`Currencies_model.php` :64-65, :85-87). `isdefault`, the base flag, is written ONLY by make-base: set on the one row and cleared on every other in one database transaction (`setBase`, `Currencies_model.php` :153-161); a create leaves it 0. `id` is assigned by the database. Perfex's own screen was its one writer (plan 04.1-27): no co-writer.

## Read-only sources

`CURRENCY_REFERENCES` (the repository's docblock) is the ONE reference register (D-40, Currencies planning answer 1; plan 04.1-27's evidence): every column that refers to a currency, listed once, each a Perfex or Perfex-module column, read only and never written. Before every usage read ONE `information_schema.COLUMNS` probe (every table and column name bound) answers which lines the connected schema has and with which `DATA_TYPE`; only those run, a missing one counts 0 and raises no error, and the probe is never cached (D-28). This module never adds or drops a column anywhere.

The first seven are Perfex's own list (`App.php:518-547`) and the make-base rule's input (D-39). Purchase stores the converted-from and converted-to currency as the id's decimal text (`Purchase_model.php` :1256, :1396, :1791, :2004), and fixed_equipment's location select is valued by id; the rate tables, their logs and the payslips store the currency's CODE. Matching is exact: an integer line on an integer column binds the ids as numbers; any other line compares the bytes with `CAST(r.<column> AS BINARY) IN (...)` against each id's decimal text or each row's stored code, so `'07'`, `'7 '`, `usd` and `USD ` never count for `7` or `USD`. An error from the probe or any statement rejects the whole read (fail closed).

The exchange rates, their logs and the payslip code snapshots never block a delete (D-40: configuration and history, as D-33 excluded the accounting mappings; Perfex counts only its seven core columns), but they DO lock a code change (D-42 widened, answer 2): a renamed code would orphan the by-code rate lookups and change what past documents show. Not in the register: `tblcheque_management.currency` (answer 3: no code writes it; a line is added if a writer appears) and `tblacc_checks.currency_display_name` (a typed label, not a reference).

## Facade surface

- `describe(): { module: 'currencies'; version: 1 }`
- `registerUsage(counter: CurrencyUsageCounter): void`: another module's read-only usage counter `{ key, module, noun, count(currencyId) }`, registered from that module's own `onModuleInit` (D-41 inverted, the `MailFacade.register` precedent); a malformed or duplicate key throws at boot. Every registered counter is asked for each id: a delete is refused (`ERP-CURRENCIES-0003`) and a code change locked (`ERP-CURRENCIES-0005`) while one answers more than 0, and a counter that fails refuses both. No module registers one today.
- `listAll(): Promise<readonly Currency[]>`: every currency, the id ascending; refused loudly (`ERP-INTERNAL-0001`) above `CURRENCIES_FACADE_MAX_ROWS` (1,000), never truncated (D-44).
- `baseCurrency(): Promise<Currency | null>`: the first `isdefault` row by id, or `null` (D-44; branding reads it).

`Currency` is `{ id, name, symbol, decimalSeparator, thousandSeparator, placement, isBase }`, the separators and the placement as stored (`null` for NULL), never a count or the wire DTO. No facade method writes a currency or asserts the administrator flag: a module-to-module call has no actor. Other modules import only `src/v1/currencies/index.ts` (the facade and the `Currency`, `CurrencyId`, `CurrencyUsageCounter` types) and `CurrenciesModule`, which imports no v1 module, so no import cycle can form.

## Endpoints

Under `api/v1/currencies` (`CURRENCIES_ROUTES` in `currencies.routes.ts`). All seven are administrators only (D-06, D-38): every handler carries `JwtAuthGuard, PermissionGuard` and declares no permission code, and the service asserts the administrator flag as the first statement of every use case, so a member holding every catalogue code is still refused. Perfex's own controller was administrator-only too (`Currencies.php:11`). `@erp/contracts`' `ROUTE_GATES` declares the three screens `'admin'` and `__tests__/route-gates.spec.ts` compares every handler with it. Every failure is an RFC 9457 problem (`application/problem+json`) with an `ERP-*` code: 400 `ERP-VALIDATION-0001` (+ `issues`), 401 `ERP-AUTH-0004`, 403 `ERP-AUTH-0005` (detail `currencies are managed by administrators only`).

| Method   | Path       | Success                                                                                                                                                                                               | Errors beyond the three                                                                 |
| -------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `GET`    | ``         | 200 `{ data, meta: { nextCursor, prevCursor, total, rangeStart, exportLimit, printLimit } }`, each row the record; `?limit&cursor&q&sort` (`-name` default, `name`, `symbol`, `-symbol`, `id`, `-id`) | none                                                                                    |
| `GET`    | `export`   | 200 by `?format=`: `csv` (absent), `xlsx`, `pdf` (each `attachment; filename="currencies-YYYY-MM-DD.<ext>"`) or `print` (JSON rows, no attachment); `no-store`; columns `name`, `symbol`, `isBase`    | 400 on `export` over the format's cap; on `key` (no row selection); on `font` for a PDF |
| `GET`    | `:id`      | 200 the record                                                                                                                                                                                        | 404 `ERP-CORE-0004`                                                                     |
| `POST`   | ``         | 201 the record                                                                                                                                                                                        | none                                                                                    |
| `PATCH`  | `:id`      | 200 the record                                                                                                                                                                                        | 404 `ERP-CORE-0004`; 409 `ERP-CURRENCIES-0005`                                          |
| `PATCH`  | `:id/base` | 200 `{ id, isBase: true }`                                                                                                                                                                            | 404 `ERP-CORE-0004`; 409 `ERP-CURRENCIES-0004`                                          |
| `DELETE` | `:id`      | 204, no body                                                                                                                                                                                          | 404 `ERP-CORE-0004`; 409 `ERP-CURRENCIES-0001`, then `0002`, then `0003`                |

The record is `{ id, name, symbol, decimalSeparator, thousandSeparator, placement, isBase, usage, lockUsage, registeredUsage, canMakeBase }`: the id as text; the code, the symbol, the separators and the placement as stored (`null` for NULL); `usage` the 24 delete-counting groups and `lockUsage` the three lock-only groups of the register; `registeredUsage` each registered counter's answer by key (`{}` today: none is registered); `canMakeBase` true when the row is not the base and the current base has no use in Perfex's seven core columns. The body of `POST` and `PATCH :id` is Perfex's five fields, strict: `name` through the shared code schema (trimmed, then `a` to `z` upper-cased as PHP 8's `strtoupper`, 1 to 3 characters; a 400 on `['name']` with `required` or `at most 3 characters`), a code another currency holds accepted; `symbol` 1 to 10 characters holding a non-space character, stored as sent; `decimalSeparator` one of `,` `.`; `thousandSeparator` one of `,` `.` `'` (none) and a space; `placement` `before` or `after`; any other key (`isBase`, `isdefault`, `id`, ...) is a 400. `PATCH :id/base` takes an empty strict body. `q` matches the code or the symbol (contains, under the columns' collation) and, when all digits up to 2147483647, the id.

The refusals and their details (counts and plain words only):

- `ERP-CURRENCIES-0001` (DELETE): `used by N invoice(s), N expense(s), N proposal(s), N estimate(s), N customer(s), N credit note(s), N subscription(s), N purchase order(s), N purchase request(s), N purchase quotation(s), N purchase invoice(s), N debit note(s), N FAF request(s), N vendor(s), N goods receipt(s), N goods delivery note(s), N packing list(s), N order return(s), N fixed equipment cart(s), N payslip(s) converted from it, N payslip(s) paid in it, N purchase document(s) converted from it, N purchase document(s) converted to it and N fixed equipment location(s)` (non-zero groups only).
- `ERP-CURRENCIES-0002` (DELETE): `it is the base currency; make another currency the base first`.
- `ERP-CURRENCIES-0003` (DELETE): `used by N <noun>(s); remove them first` (each registered counter above 0, by key order).
- `ERP-CURRENCIES-0004` (make-base): `the base currency is used by <the non-zero core groups>; Perfex does not allow changing the base currency once it has transactions`.
- `ERP-CURRENCIES-0005` (PATCH, a code change): `it is in use (<every non-zero group of usage and lockUsage, with N exchange rate reference(s), N exchange rate log reference(s) and N payslip(s) showing its code, then each registered counter above 0>), so its code cannot change: past records would show another code; the symbol, the separators and the placement can`.
- Any of the five, when a count cannot be read: `its use could not be counted`. Nothing is written and no event is published on a refusal.

## Events published

| Event                           | When                                     | Payload                                             |
| ------------------------------- | ---------------------------------------- | --------------------------------------------------- |
| `currencies.record.created`     | after `POST` stores it                   | `{ id, at }`, `CurrenciesCreatedV1`                 |
| `currencies.record.updated`     | after `PATCH :id` saves it               | `{ id, at }`, `CurrenciesUpdatedV1`                 |
| `currencies.record.baseChanged` | after `PATCH :id/base` switches the base | `{ id, previousId, at }`, `CurrenciesBaseChangedV1` |
| `currencies.record.deleted`     | after `DELETE` removes it                | `{ id, at }`, `CurrenciesDeletedV1`                 |

Declared in `events/published.ts` (`CURRENCIES_PUBLISHED_EVENTS`), published through `DOMAIN_EVENT_PUBLISHER` from `service/currencies.transport.ts` after the write. A payload carries ids and the server time, never the code, the symbol or a count. Branding drops its memo on `baseChanged` and `updated` (D-44, answer 6). After each publish the service writes one `LoggerService.log` line, `currency created|updated|deleted` with `{ id }` or `base currency changed` with `{ id, previousId }`, which carries `requestId` and `staffId` from the request context (D-43, BE-10). Node writes no row to Perfex's activity log, where Perfex wrote one per add, edit and delete (`Currencies_model.php` :68, :89, :129): the event and the log line are Node's record (D-43, D-18), a release-note item.

## Events subscribed

None. Listed in `events/subscribed.ts` (`CURRENCIES_SUBSCRIBED_EVENTS`). Other modules' uses reach this module through the registered counters, not through events.

## Jobs

None.

## Resilience

- **Breaker:** none: no outbound HTTP, no vendor call; the registered counters are in-process calls into the modules that registered them.
- **Retry policy:** none on writes: an unkeyed `POST` retried could create two rows, and the events are in-process.
- **Pool budget:** shares `POOL.db.api` (`connection_limit` in `DATABASE_URL`, asserted by `check:db`); a list page costs the page, two counts, the probe and one statement per present register line (40 at most) in one `Promise.all`, the base state (one `findFirst`, then the base's own register read) and each registered counter per page id; no extra DB or Redis client.

## How to run its tests

```bash
corepack yarn test src/v1/currencies          # unit, the register against the schema, the repository over a stub client, the gates and the in-process controller e2e spec (no network, no database)
corepack yarn test:int src/v1/currencies      # the repository against the local stack (node ../erp-infra/scripts/local-up.mjs first)
```

The int spec writes only `tblcurrencies` rows with a marker code (`ZZA`, `ZZB`, `ZZC`) and the marker symbol `zz-int-28`, deletes them before and after the run, refuses to start if a real row holds a marker code, and runs the base switch inside a transaction it rolls back; it never writes a Perfex-owned table and never reads a local value into an assertion message.
